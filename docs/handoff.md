# 開発引き継ぎ

「ぼくのかんがえたちょうさいきょうの武器（仮称）」は、自作武器を戦わせるレトロ風の対戦バカゲーです。武器名・単一属性・自由記述の特殊能力を入力し、相性と運、低確率のハプニングで勝敗が決まります。**MVP第2段階まで実装済みで、次は1台のブラウザで2人が試遊できる第3段階です。**

## 決定事項と実装済みの範囲

- **構成** — 判定はPythonにまとめ、画面にはFlaskとJinjaを使う方針です。Pythonを学びながら追える小さな構成を優先します。初期の対戦はAI利用料ゼロで、外部通信の待ち時間がなく、固定シードで検証できます。
- **第1段階** — 固定の2武器によるCLI対戦を実装済みです。入力検証、外部設定の属性相性、能力解析、反射と直接攻撃の相性、未分類能力への基本点、明確な無条件勝利能力などの爆散判定が動きます。能力解析は対応する短い表現に限られます。
- **第2段階** — 武器固有の運、能力による運補正、試合ごとの運を別々に計算します。通常得点の確定後にイベントを1回抽選し、条件不成立なら終了します。演出・得点補正・勝敗変更の初期イベントをJSONで調整できます。爆散は通常判定と抽選に先立って決着します。
- **コードの入口** — [CLI](../main.py) から [勝敗判定](../game/battle.py) の `resolve_battle()` を呼びます。[能力解析](../game/abilities.py) の `analyze_ability()` が能力の特徴を返し、[イベント](../game/events.py) の `select_event()` が該当イベントを選びます。設定は [属性相性](../data/elements.json) と [イベント定義](../data/events.json)、検証は [基本判定テスト](../tests/test_battle.py) と [運・イベントテスト](../tests/test_luck_and_events.py) を参照してください。

### 基準動作の確認

リポジトリのルートで実行します。Cloudに `python` がなければ `python3` を使います。第2段階の実行に外部ライブラリは不要です。

```sh
python -m unittest discover -s tests -v
python -X utf8 main.py --seed 149
python -X utf8 main.py --seed 795
```

基準コミットの確認結果は26件すべて成功。固定サンプルでは `149` で覚醒して補正後2対2、`795` で隕石が落ちて通常得点2対1のまま引き分けになります。

## 次の作業候補と未決定事項

**次の実装候補は設計書 §7 の第3段階です。** Flaskで1台のブラウザ上の2人分の入力、結果、再戦をつなぎます。既存の `resolve_battle()` を使い、無効な入力から戻れること、最終勝敗と理由が一致すること、入力を引き継いだ再戦が新しいシードで動くことを確認します。Flaskの画面、ドット絵合成、AI API、オンライン対戦、データベースは基準コミットでは未実装です。

| 論点 | 試遊に向けた意向と保留事項 |
| --- | --- |
| 実況と数値表示 | 2人試遊では、段階的な文章の描写と、得点を前面に出さない勝因説明を重視。どの段階でどこまで演出を作るかは要確認。CLIの得点表示は現状の動作確認に使える |
| 武器名・属性・能力 | 武器名は主に見た目、属性は相性、能力は固有の効果を担う意向。名前・属性・能力の整合性をどこまで求めるかは未決定。ドット絵は32×32程度が候補 |
| 能力の相互作用と配点 | 相手によって能力の価値が変わる仕組みを検討。例は「被弾で強くなる能力」が連続攻撃には有利で、一撃必殺型には不利になるケース。戦闘ステップの要否、細かな配点やJSONでの管理は試遊後の検討事項 |
| 将来のAI利用 | 作成時に既存のPythonルールを優先し、難しい文だけAIで解析する案。攻撃形式・発動条件などを共通形式で保存し、再利用する。相性と勝敗は原則Pythonで判定する。AIに点数を提案させる範囲や誤解析の補正方法は未決定 |

今後の実装は依頼された段階ごとに進めます。開発意見ログの案は、採用を確認してから実装・企画書・設計書へ反映します。コミットやプッシュはユーザーが差分を確認した後に行います。
