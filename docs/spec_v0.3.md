# ぼくのかんがえたさいきょうの武器（仮称）
## Webアプリケーション開発仕様書 v0.3

### 1. プロジェクト概要

「ぼくのかんがえたちょうさいきょうの武器（仮名）」という、ユーザが考案した武器同士を戦わせるWebゲームを開発したい。

ジャンルはレトロゲーム風のカジュアルな対戦バカゲー。

ユーザが設定できるのは、武器名・属性・特殊能力の3項目のみとする。

武器の情報からシステムが性能や相性を評価し、複数の判定基準とランダム要素によって勝敗を決定する。

勝敗が確定した後は、実況風のテキストとドット調のエフェクトで戦闘を演出する。

強い武器が必ず勝つのではなく、意外な逆転や理不尽なハプニングも楽しめるゲームを目指す。

最終的にはWebブラウザから友人と遊べるゲームとして公開したいが、まずはローカル環境で動作するシンプルな試作品を開発する。

### 2. 武器作成

ユーザが入力・選択する項目：

- 武器名
- 属性（単一属性）
- 特殊能力（説明文は仮に50文字以内）

「戦い方」の入力欄は設けない。

武器名の文字数制限は今後決定する。

特殊能力は自由記述とし、攻撃・防御・回復・状態異常・運の操作など、幅広い発想を許容する。

ただし、ゲームバランスを著しく損なう能力には専用のペナルティを用意する。

### 3. 勝敗判定と運

勝敗は複数の要素を評価して決定する。

初期の判定基準候補：

1. 属性相性
2. 特殊能力の性質と強さ
3. 武器固有の運
4. ランダム要素
5. 特殊イベント

運は単純な乱数だけではなく、武器情報に応じて変化させたい。

例えば以下の要素を検討する。

- 武器名の画数
- 武器名に含まれる文字
- 特殊能力の説明文に含まれる言葉
- 特殊能力自体が運に干渉する性質を持つか

画数については、漢字以外の文字や画数の数え方に曖昧さがあるため、判定方法を検討する。

単語が含まれるだけで必ず運が上昇するなど、単純すぎる仕様にはしない。

運の値が勝敗に与える影響は調整可能にし、運だけで常に勝利する状況を避ける。

また、武器固有の運と、各試合で発生するランダムな変動は別の要素として管理する。

### 4. 属性システム

初期段階では単一属性のみを実装する。

属性数は10種類前後を想定する。

仮の属性候補：

- 炎
- 水
- 雷
- 風
- 土
- 光
- 闇
- A
- B
- C

一般的でない属性や未確定の属性は、仮にA・B・Cなどと表記する。

ポケモンのような複雑な属性相性システムは避ける。

属性間にはシンプルな有利・不利・互角の関係を設定する。

原則として、各属性の有利・不利の数を少なくし、ユーザが直感的に理解できる仕組みを目指す。

属性相性は固定的なコードに埋め込まず、設定ファイルなどで簡単に変更できるようにする。

#### 将来的な副属性

将来的には、2つの属性を組み合わせた複合属性を追加したい。

例えばA属性とB属性を組み合わせた場合、「AB属性」という独立した属性として扱う。

ポケモンのように2属性の相性倍率を掛け合わせる方式にはせず、複合属性そのものに独自の相性を定義できる構造を想定する。

ただし、初期段階では副属性・複合属性を実装しない。

### 5. 特殊能力の解析

特殊能力はユーザによる自由記述とする。

特殊能力の強さや性質を判定する方式として、以下を比較検討する。

- AI APIによる文章解析
- キーワードやルールによる分類
- 分類結果を数値化するアルゴリズム
- 上記を組み合わせたハイブリッド方式

特に、文章の意味や文脈の理解が必要な部分ではAIの活用を検討する。

AIを使用する場合は、毎試合APIを呼び出すのではなく、武器作成時に解析した結果を保存・再利用する方式を優先する。

解析結果は、攻撃・防御・回復・特殊効果・運への干渉などの項目に分類することを検討する。

最終的な勝敗は必ずしもAIに直接判断させず、解析結果とゲーム側のアルゴリズムによって決定する方式を優先的に検証する。

AIの費用、判定速度、解析精度、ゲームバランスを比較して採用方式を決定する。

### 6. 特殊イベント

バカゲーとしての面白さを高めるため、通常の能力判定とは別に特殊イベントを導入する。

イベント例：

- 審判がよそ見をしていたため一方が勝利
- 隕石が闘技場に落下し、両者引き分け
- 武器が持ち主を裏切る
- 武器の扱いに失敗して自爆
- 突然の覚醒による逆転
- 武器が暴走して予想外の結果を引き起こす

特殊イベントには、勝敗を逆転させるもの、引き分けにするもの、能力評価を変化させるものなど、複数の種類を用意する。

イベントには個別の発生確率や条件を設定できるようにする。

イベントの追加・削除・確率調整は、プログラム本体の大幅な変更なしで行える構造にする。

例えばJSONなどの外部設定ファイルによる管理を検討する。

低確率の理不尽なイベントは、毎回の対戦で頻繁に発生しないようにする。

### 7. 無敵能力へのペナルティ

「無敵」「絶対に勝つ」「何があっても負けない」「無限の力」など、ゲーム性を破壊する能力には特殊なペナルティを適用する。

基本的には、強すぎる能力に持ち主の身体が耐えられず、対戦開始時に爆散して敗北する演出とする。

例：

「強大すぎる能力に身体が耐えきれない！！」

「身体が爆散した！！」

「戦う前に決着がついてしまった！！」

ただし、特定の単語が含まれているだけで禁止能力と判定しない。

例えば「無限に伸びるが攻撃力はゼロの剣」と「すべての攻撃を無効化して必ず勝つ剣」は区別する。

否定表現、条件付きの効果、能力の代償など、文章全体の意味と文脈を考慮した判定を行う。

必要に応じてAIによる意味解析を利用し、誤判定を減らす。

### 8. 武器のビジュアル生成

武器作成画面では、完成した武器を眺められるようにする。

武器はレトロゲーム風のドット絵として表示したい。

初期段階では複雑な画像生成AIなどを使用せず、あらかじめ制作したパーツを組み合わせて武器を表示する方式を検討する。

パーツ例：

- 刀身
- 持ち手
- 鍔
- 銃身
- グリップ
- 装飾品
- 属性エフェクト

以下の3方式を比較する。

① 武器の種類だけを判定し、テンプレートから見た目を選択する。

② 武器名に含まれる言葉を判定し、テンプレートのパーツを自動的に組み合わせる。

③ ユーザがパーツを自由に選択する。

現段階では②を基本方針とし、該当する武器種が判別できない場合に①を利用する構成を優先する。

例えば武器名に「刀」が含まれる場合は刀系のパーツ、「銃」が含まれる場合は銃系のパーツを使用する。

特殊能力や属性に応じて色やエフェクトを変化させることも検討する。

③の手動選択方式は、作成時間が長くなりゲームのテンポを損なう可能性があるため、初期段階では採用しない。

武器のパーツは容易に追加・変更できるようにする。

完成した武器は武器作成画面と対戦画面に表示する。

### 9. 戦闘実況と演出

戦闘は、複数の判定基準を順番に評価しながら進行する形式を基本とする。

例：

「炎属性は風属性に有利だ！！」

「しかし、2Pの特殊能力『生命吸収』が発動！！」

「失われた体力が回復した！！」

「ここでまさかの隕石が落下！！」

「闘技場が消滅！！」

「両者引き分け！！」

判定結果に対応する実況テキストをあらかじめ複数用意し、組み合わせる方式を検討する。

AIに毎回実況の全文を生成させることは必須としない。

UIには以下の演出を取り入れる。

- テキストの段階的な表示
- ドット調の攻撃エフェクト
- 画面の揺れや点滅
- 属性に応じた色の変化
- 勝利・敗北・引き分けの演出

戦闘終了時には、属性・特殊能力・運・イベントなどを総合した勝敗理由を表示する。

### 10. 画面構成

初期段階では以下の画面を想定する。

1. タイトル画面
2. 武器作成画面
3. 対戦画面
4. 結果画面

武器作成画面には、武器名・属性・特殊能力の入力欄と、作成した武器のプレビューを配置する。

複雑なカスタマイズ画面は設けず、なるべく少ない操作で対戦を開始できる設計とする。

対戦画面では双方の武器画像、武器情報、実況、エフェクトを表示する。

結果画面には勝者と勝敗理由を表示する。

初期段階では1台の端末で2人分の武器を入力するローカル対戦形式とする。

### 11. Web公開と機能範囲

将来的にはブラウザ上で公開し、友人と気軽に遊べるゲームにしたい。

ただし、以下の機能は現段階では実装しない。

- オンライン1対1対戦
- トーナメント
- 対戦履歴
- ランキング

これらは初期開発の対象から除外し、将来的に必要性が生じた際に改めて検討する。

最初は対戦機能そのものの完成度を優先する。

### 12. 技術方針

- 最初はローカル環境で実行できる構成にする。
- Pythonの活用を優先的に検討する。
- 将来のWeb公開を考慮した設計にする。
- 判定システムと画面表示処理を分離する。
- AI APIの利用回数・費用を抑える。
- APIキーは公開せず、安全に管理する。
- 属性相性やイベント確率は外部設定から調整できるようにする。
- 乱数の再現性を確保できるようにする。
- テストによってイベントの発生頻度や判定バランスを検証する。
- ゲームデザインは初期段階ではシンプルにする。
- 各要素は変更・追加・削除しやすい構成を優先する。

### 14. 開発段階

フェーズ1：
ローカルで動作する最小限の武器作成・対戦アプリを作成する。

フェーズ2：
属性相性、特殊能力解析、運、特殊イベントの判定システムを実装・調整する。

フェーズ3：
武器のドット絵パーツの組み合わせとプレビュー機能を実装する。

フェーズ4：
実況演出、戦闘エフェクト、UIデザインを改善する。

フェーズ5：
ブラウザで公開できる形式に整え、友人に遊んでもらいながら調整する。

### 15. Codexへの指示

本仕様書は開発構想であり、未確定の部分が多く存在する。

実装前に、仕様の矛盾点、技術選定、設計上の問題点を整理すること。

AI APIの利用を前提とせず、アルゴリズムのみで実現できる部分も検討すること。

特に勝敗判定の公平性、自由記述の能力解析、イベントの拡張性、武器画像のパーツ合成について複数案を比較すること。

初期段階では最小限の機能だけを実装し、段階的に機能を追加すること。

変更を容易にするため、機能ごとに処理を分離し、初心者にも理解しやすいコードと説明を心がけること。
